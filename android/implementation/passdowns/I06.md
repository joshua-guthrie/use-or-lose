## Research findings that shaped the brief

- The desktop core already exposes everything the phone needs as **pure, reusable functions**: `cross_year.manual_ledger(year, start, annual_accrual, balances, pay_periods, config)` builds a complete schema-v1 independent manual ledger (validates increment/ranges, seeds accruals, no file I/O); `ledger.upsert_accrual_rate_change(leave_year, category, effective_date, hours_per_pay_period, reason)` handles the Today-balance dated rates; `cross_year.seed_accruals` and `ledger.calculate_balances` complete the Today flow; `commands/forced_balance.py` defines the canonical forced-balance row (direction `forced_increase`/`forced_decrease`, source `forced-balance`, setup reason, unique ID). The CLI `init` (`commands/data.py`) is the reference wiring.
- The read facade (`read_api`) is deliberately read-only; the proposed write surface is a new Android-side bridge module (`bridge/src/fedleave_creation.py`) that only calls those existing functions — no `src/fedleave` changes, no new accounting logic (P-D1).
- Holiday caches: bundling `holidays.py`/`holidays` now is avoidable; a missing cache simply means no holiday markers until I18 (spec-sanctioned) — P-D2.
- Empty-store config: `config.init_config` can run into a temp dir inside the bridge to produce the first-use `config.json` bytes — P-D3.
- The stale-preview/duplicate-creation contract rides on I04's `beginCandidate`/`publish` with the generation fingerprint and a target-year-absence recheck — P-D4.
