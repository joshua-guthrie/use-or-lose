## Start or find a leave year

**CAL-YEAR-01 · Prompt from the current task.** Resolve the selected date against each valid ledger's inclusive start and end dates. For example, January 9, 2027 still belongs to the example 2026 leave year. Check on launch, when **Today** changes to an uncovered date, and when the user accepts a future balance date or begins an action that needs an uncovered future date. Offer **Set up leave year** from that context. Month browsing and passive reports read existing data only. An uncovered past date offers an explicit setup action when appropriate. A corrupt file, overlapping ranges, or a missing linked source needs a data issue message and a way to review or restore data.

For first use, offer **Restore backup** or **Set up leave year**. I06 delivers working setup on its own. I08 wires the editor entry after setup, and I17 adds Restore backup to Welcome. For an existing store, propose the immediately adjacent successor when its predecessor is valid. Show the proposed year identifier, full date range, first pay period, and schedule count. The successor starts the day after the predecessor ends. When there is no verified schedule or the suggestion misses the requested date, ask the user to verify the actual first pay-period date and count. For several consecutive missing years, guide the user through each year in order and review each before creating it. Keep any year already confirmed if the user stops midway. Discarding an unconfirmed proposal leaves the existing ledgers intact. For a cancelled future balance selection, resume the previous selection. If Today itself is uncovered, keep today's date visible with a setup action and unavailable balance. After creating the year that contains the requested date, resume the balance lookup or return to the editor with its original draft. Entry changes still require their own Save. A competing creation prompts a reload and revalidation of the target. The CLI continues to require explicit year creation. [Issue #149](https://github.com/joshua-guthrie/fedleave/issues/149) · [Desktop date resolution](../../../../src/useorlose/cli_helpers.py#L156) · [Desktop first load](../../../../src/useorlose_gui/main_window.py#L1372)

**YEAR-MAN-01 · Set up an independent starting balance.** For a new independent ledger, ask for the actual first pay-period date and suggest 26 periods with an option for 27. Confirm the resulting contiguous schedule, annual accrual and configured sick rate. Give the user an explicit choice of **Balances at start of leave year** or **Balances as of Today** when the schedule contains Today. The first choice puts the entered hours at the start of the year and calculates normal accrual from the schedule. Unspecified starting-balance quantities are zero. Require finite nonnegative hours at the configured increment. Existing years are create-only. Manual lineage has no predecessor, and a later discovery of an older file does not change it. An undated expiring starting balance such as travel comp can retain its numerical balance and must warn that the earning date and expiration are unavailable. PPL and FMLA require dated events. [Manual creation rules](../../../../README.md#manual-starting-balances) · [Manual fixture tests](../../../../tests/test_leave_year_creation_manual.py)

### Balances as of Today

**YEAR-TODAY-01 · Start from a verified balance today.** Offer **Balances as of Today** only when creating a new independent leave-year file whose stored date range includes the current local date. Display the actual date and let the user enter the exact hours they have by balance category. A blank value is zero. Use the same hour validation as the start-of-year option and reserve PPL, FMLA and usage-only categories for their existing workflows. Report the original earning date and expiration as unknown for any accepted undated expiring amount. [Setup mockups](../01-calendar/01-03-navigation-and-screens.md#choose-the-balance-date-at-setup)

- Keep the actual leave-year bounds and pay-period schedule. On creation, show zero balances and no generated leave activity from the year start through the day before Today. This applies even when the user enters nonzero balances for Today. Preserve dates, pay periods and holiday markers. Record the entered amounts on Today. If an accrual is scheduled for Today, the target includes that accrual and must still be exact. After Today, use the configured annual and sick rates on their normal accrual dates. Subsequent explicit ledger edits can change the dated results.
- Build one candidate using schema-v1 JSON and independent manual lineage. Keep the starting balance maps at zero, record `initialization.baseline_as_of` as an additive ISO date, set the base annual and sick rates to zero and put the configured rates in dated `accrual_rate_changes` effective Today. Seed the scheduled accruals from those rates through year-end. For each supported balance, compute the difference between its target and its generated balance through Today. Use the existing reconciled `forced-balance` increase or decrease dated Today for a nonzero difference, with a setup reason and a unique ID. Avoid zero-hour rows and invented historic earning events. The normal rate remains effective at year-end for a future successor. [Dated rate and accrual helpers](../../../../src/useorlose/ledger.py#L381) · [Desktop forced balance](../../../../src/useorlose/commands/forced_balance.py#L16)
- Review the schedule, effective date, target amounts, zero period before Today, next scheduled accrual when present, and any provenance warning before **Create leave year**. Preview and Cancel write nothing. Under the storage writer, recheck that the target year is still absent and the reviewed schedule, local date and settings still match. If the local date rolled over, refresh the preview and get a new confirmation. Publish the validated schedule and balances together. [Private store and recovery](../04-architecture/04-02-device-storage.md#write-and-recovery-model)

### Carry over from a previous leave year

**YEAR-CARRY-01 · Carry over a reviewed closing balance.** Offer **Carry over from previous leave year** as the suggested choice when the adjacent source and its schedule validate. Keep the manual option available and require an explicit choice if carryover is blocked. Carryover uses the validated source end, canonical next schedule or explicit 26/27-period agency schedule, and annual and sick rates in effect at source close. Present the source dates, destination dates, starting balances by category, reductions and reasons, carried lots, and warnings. Preview reads without writes. On confirmation check that the reviewed source, destination, and policy still match and that the destination is absent. Refresh a stale preview and ask for confirmation again. Write the new year once and keep the source unchanged. [Desktop preview and apply](../../../../README.md#carry-over-from-previous-leave-year) · [Creation tests](../../../../tests/test_leave_year_creation_carryover.py)

| Category | Rules reflected in the review |
| --- | --- |
| Annual, sick, credit | Apply the configured balance policy. Default annual cap is 240 h, sick carries in full, and credit caps at 24 h. Show the category and hours of any reduction. Count the authoritative starting balance once when legacy transactions mirror it. |
| Comp, travel comp, restored annual, time-off award | Carry remaining eligible lots, including nonexpiring awards when allowed. Preserve the source year and transaction, original dates and hours, applicable deadlines, and approved extensions. Keep restored annual separate from annual. |
| Religious comp, activity types, and unknown categories | A material religious-comp balance requires an explicit agency carryover policy. Usage-only categories keep their history in the source and yield no positive starting balance. Surface unsupported policies and missing provenance for review. |
| PPL and FMLA | Preserve linked parental history and eligible PPL windows under the rules below. FMLA usage has no starting-balance entitlement credit. |

**YEAR-REC-01 · Reconcile a linked chain.** A source edit or applicable policy change can make stored openings stale. Show the read-only recalculation and warning when the chain can be resolved. Expose **Review carryover** from that warning and from leave-year maintenance. Show affected successors, before and after openings and lots, proposed removals, and conflicts. Confirmation applies the reviewed change to generated carryover records and leaves genuine destination activity and additive fields intact. A manual boundary stops the chain. Legacy ledgers of unknown lineage need explicit review. A missing source or consumption beyond the revised entitlement blocks apply and identifies the underlying issue. A second unchanged apply leaves files unchanged. Require backups before changing existing ledgers, recoverable multi-year writes, and a visible recovery state after interruption. Recover original data first, then generate a fresh preview. [Desktop reconciliation and recovery](../../../../README.md#preview-source-edits-and-reconciliation) · [Reconciliation tests](../../../../tests/test_cross_year_reconciliation.py)

**YEAR-OPEN-01 · Correct a starting balance.** In leave-year maintenance, show old and proposed opening hours and require a reason. For a manual or independent legacy ledger, update its single authoritative opening. For a linked year, direct the user to the source and carryover review. For an expiring category with missing provenance, direct the user to the original dated entitlement and explicitly account for any undated hours already in the balance. [Starting-balance command](../../../../src/useorlose/commands/starting_balance.py)

## Edit and review leave

Phone forms use full leave-type names, a dated heading, positive hour fields with labeled directions, and a local comment field. Show the configured increment and leave the draft visible when validation or saving fails. Handle an existing supported value without silently clamping its hours. Treat comments and reasons as text in the app and canonical JSON. Preserve quotes and punctuation, apply the shared text validation, and keep comments out of routine diagnostics. Show success after the ledger write completes and refresh the ledger views from the saved state.

Use the same fields, labels, formatting, actions and spoken descriptions for effective leave before, on, and after Today. The date supplies the time context. Use the same rule in Calendar, History, Reports and their shared artifacts. Preserve stored status and other provenance during restore, correction, and writeback. Show denied, cancelled and legacy voided records as ineffective in history, where that distinction explains why they contribute zero. A future **Projected balance** describes the balance calculation at its cutoff.

**CAL-DAY-01 · Edit Day.** Open the editor directly from the selected Calendar date. Let the user choose one group of ordinary editable entries before entering a new total. Label the group by leave type and direction. Scope it to that leave year and date. Combine rows only when a replacement preserves their stored status, source, shared comment and required metadata. If metadata differs, show the individual rows in the same dated layout and open the individual correction review for the chosen ID. Keep ineffective records in history. Show automatic accrual, forced adjustments, generated carryover and expirations as separate activity with links to their workflows where available. [Desktop editor and review](../../../../src/useorlose_gui/main_window.py#L324) · [Desktop replacement behavior](../../../../src/useorlose/commands/transactions.py#L67)

Prefill the chosen group's total and shared comment. Use the configured hour increment. Review the affected IDs, old and new hours, and the retained or deliberately changed comment. A replacement keeps the selected date, category, direction, status, and preserved source. Zero clears only the selected group's rows. After confirmation, every other ID, comment and stored field remains intact. If the selected rows, their membership, or relevant accounting data changes after review, require a fresh review and preserve the draft. Back or cancellation during review returns to the draft. Discarding the editor preserves the ledger. Use **Add entry** for new records.

**CAL-DAY-02 · Add an individual entry.** Use **Add entry** for any date. Use the supported category and direction rules and the same default effective status on every date, the core's `planned` default in schema v1. The form has no status field for ordinary entry. Include the entry in a dated result once its date falls within the range. Denied, cancelled and legacy voided entries contribute zero balance effect and physical absence. [Desktop add](../../../../src/useorlose/commands/transactions.py#L162) · [Transaction effects](../../../../src/useorlose/transaction_effects.py)

**CAL-HISTORY-01 · View transactions.** From Calendar's Menu, open the browsed month as the initial inclusive start/end range. From a period detail, use the period dates. Show applicable rows across leave years in date and ID order by default. Each effective row shows date, leave type, direction and hours in the same layout. Details show source, full description and identity. Identify ineffective rows and generated records. Distinguish an empty range from an unavailable ledger. Allow sorting as on the desktop. Enable editing actions only for eligible rows. [Desktop range view](../../../../src/useorlose_gui/main_window.py#L1245) · [Desktop range selection](../../../../src/useorlose_gui/main_window.py#L2350)

**CAL-TX-01 · Correct or delete an individual entry.** Scope the selection by the stored year and transaction ID so multiple entries on one date remain distinct. **Correct entry** reviews the chosen row's date, type, direction and hours with a required explanation and retains its ID. If the proposed date belongs to another leave year, explain the date restriction and let the user add to the proper year and review the original separately. **Delete entry** confirms the chosen row and removes it from the active ledger, matching the desktop command named `void`. Show the effect on dependent years and send generated entries to their source or relevant maintenance action. Revalidate the target if it changes while the review is open. [Desktop correction](../../../../src/useorlose/commands/transactions.py#L605) · [Desktop deletion](../../../../src/useorlose/commands/transactions.py#L926)

**CAL-FORCE-01 · Force a verified balance.** Open from the Calendar menu or leave-year maintenance. Choose an effective date, a leave type and a target in hours, then review the required difference before applying. The adjustment keeps original history and uses the selected date. [Force Balance rules and screens](../01-calendar/01-06-force-balance.md)

An advanced **Reconcile entry** action lets the user enter and review a payroll change with its reason and source. If several rows match the date, category and direction, the user picks the exact transaction. ## Accrual, caps, and expiration

**YEAR-ACC-01 · Change an accrual rate.** Review the year, category, effective date, previous rate, and proposed rate. Offer annual and sick in the same maintenance form. The desktop GUI exposes annual changes and the core supports both. Use the most recent rate effective on the configured accrual date, normally period end. An earlier closing period keeps its rate and a later scheduled change still applies on its date. Replacing a change for the same date and category does not create a duplicate. Dates outside the year and invalid hours require correction. Synthesize missing automatic rows for dated reads without writing the store. Use the accrual editor for changes to automatic rows. [Desktop accrual editor](../../../../src/useorlose_gui/main_window.py#L2009) · [Core accrual rules](../../../../src/useorlose/ledger.py#L382)

**YEAR-CAP-01 · Review annual use-or-lose.** Show the year-end forecast date, projected annual balance, applicable annual cap, projected amount carried, and projected excess. Use the dedicated desktop Calendar use-or-lose calculation, which includes effective scheduled transactions through leave-year close. The desktop month payload also has an accrual forecast that holds other activity to today. The phone uses the dedicated calculation for **Use or lose** and shows its date alongside the result. A forecast is read-only. Lot-based expiration remains an individual deadline calculation. [Desktop use-or-lose command](../../../../src/useorlose/commands/balances.py#L354) · [Desktop Calendar call](../../../../src/useorlose_gui/main_window.py#L1653)

**EXP-01 · Review expiring leave.** Show the selected as-of date, earliest deadline, expiring hours by relevant pay-period thresholds, and expired or forfeited totals. Expose each lot's original and remaining hours, earning date, last eligible day, first ineligible day, and applicable estimated hours per pay period. Comp and travel comp use the configured number of periods after the earning period. Restored annual uses the end of the configured later leave year. Time-off awards can be nonexpiring or follow the configured policy. Allocate ordinary use to eligible lots by earliest expiration, then original earning date, then transaction ID. Respect valid explicit links. Repeated reads use copies, so they cannot double-count use or persist an expiry row. Follow the configured warning or disposition from the day after the last eligible date. Show missing provenance or unmatched usage when applicable. Bring across desktop's once-daily urgent in-app reminder and user-configurable thresholds. [Expiration engine](../../../../src/useorlose/expirations.py) · [Desktop status and reminders](../../../../src/useorlose_gui/main_window.py#L2097) · [Lot tests](../../../../tests/test_cross_year_lot_accounting.py)

**EXP-02 · Record an approved extension.** An eligible lot detail shows the current date and extension history. Review a later deadline and require the user's reason. Preserve the original date and record the approved change in the compatible fields. Preserve permitted extensions in carryover and reconcile dependent lots when a source change affects them. PPL expiry cannot be extended. [Desktop extension operation](../../../../src/useorlose/commands/expirations.py#L109) · [Extension tests](../../../../tests/test_expirations.py)

## Paid parental leave and FMLA

**PARENT-01 · Record and show PPL windows.** Earn records a dated entitlement anchored to the entered qualifying date. The desktop offers 480 h as an editable 40-hour-tour example. Use the recorded tour and the 12-workweek basis where applicable. PPL use debits every active event window, so overlapping windows provide the minimum remaining allowance, including zero, across those windows. An eligible window can cross leave years through an explicit lineage link. Carry its original dates, hours, tour, and identity. Convert remaining weeks to hours for the current tour when applicable. Show the last eligible day immediately before the calendar anniversary, the first ineligible day, scheduled hours, and potential or actual unused loss. Reject duplicate grants for the same date and invalid windows. A day with both a grant and use must show them distinctly so an edit to one preserves the other. [Parental accounting](../../../../docs/ARCHITECTURE.md#ppl-and-fmla-accounting) · [Parental behavior tests](../../../../tests/test_parental_leave.py)

**PARENT-02 · Track FMLA without double-counting absence.** PPL use contributes to FMLA once. Separate manual FMLA entries describe additional non-PPL tracking. Before adding same-day overlap, ask the user to confirm those are additional hours. Declining leaves the draft open and saves nothing. FMLA periods start with first use, independently of the PPL grant date. Show recorded usage, confirmed versus provisional periods, and remaining capacity when the history and tours verify it. Show **Unavailable** and the reason when coverage or a linked source is incomplete. Distinguish FMLA tracking from physical absence totals. Keep status on the originating records, so denied, cancelled, or voided use does not establish capacity periods. [Parental guide](../../../../docs/PARENTAL_LEAVE.md) · [Parental acceptance evidence](../../../../tests/test_parental_specification.py)
