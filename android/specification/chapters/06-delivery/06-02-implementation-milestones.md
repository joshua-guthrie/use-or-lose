# Chapter 06.02 · Implementation milestones and release decisions

This is the order of work after the owner reviews the specification. Each row targets one five-hour usage window and ends with a verifiable outcome. If a row grows, split it by the first unresolved dependency or by a user flow and finish a coherent subset. Use the measured five-hour balance to judge whether to start another increment. Complete each session's closeout while at least 30% remains. At every increment, record what passed, relevant commits, unknowns, remaining usage, and the exact next step in the root `passdown.md` and a numbered implementation note. Commit the verified increment before starting the next.

Start each milestone or subset with a [self-contained implementation brief](../05-quality/05-02-quality-gates.md#make-each-milestone-executable-from-a-brief) suitable for a smaller coding model. Every milestone and separately completed subset must pass the [QA completion gates](../05-quality/05-02-quality-gates.md#required-gates). Use the [implementation briefs index](../../../implementation/briefs/README.md) for task handoffs. A partial checkpoint or a passdown records work in progress and leaves the milestone open. The final QA and AI code review reports identify the tested candidate and link the evidence before completion.

## Review menu navigation before I01

Set aside dedicated specification review time before Android coding. Start at the [Calendar main screen](../01-calendar/01-01-main-screen.md) and walk each task one tap at a time with the owner. Use the existing screens as the starting draft.

| Starting control | Paths to review |

| Calendar upper-left Menu | **Today**, **Transactions**, **Force Balance**, and **Preview month PDF**. Show what opens and where Back returns. [Calendar dropdown](../01-calendar/01-05-menu-and-pdf.md#open-the-calendar-menu) |
| Bottom **Reports** tab | **Summary**, **Seasonality**, **Calendar heatmap**, **Overtime, comp and credit**, **Cumulative usage**, **Balance charts**, **Yearly comparison**, and **Month report**. Show the list location, year and filter selection, chart expansion where applicable, and return to the report and Calendar. Confirm whether the **Reports** label makes analytics easy to find. [Reports list](../03-reports-data/03-02-report-screens.md#reports-list-and-summary) |
| Bottom **Settings** tab | **Calendar preferences**, **Accounting and leave years**, **Holidays and reminders**, **Data and backups**, and **Help and about**. Trace commonly used actions to their final screen. Confirm the wording of **Help and about**, including the path to offline Help and the date marker legend. [Settings screens](../03-reports-data/03-03-data-and-settings-screens.md) |

Begin with a five-hour specification milestone for Calendar, Settings and Help. Use a separate milestone for Reports if the detailed walkthrough needs more time. Produce a route table with the visible label, tap order, destination, Back behavior, and state to retain. Add annotated navigation boards that start on Calendar and show each menu or list opened by a tap. Cross-check them against the acceptance cases, including large text and TalkBack order. Present the routes and any alternate labels to the owner, record decisions in a passdown, and commit each verified milestone. I01 can start after the owner reviews the resulting navigation and approves implementation.

Let the user choose start-of-year balances or exact balances as of Today for an eligible new ledger. For a known valid adjacent year, offer its calculated successor and carryover review. | Project owner when reviewing setup screens |
| Accounting controls | Keep annual and sick rate editing in a shared advanced form. First release configuration edits target the work tour, time increment, supported defaults and FMLA history. Show agency policy used and preserve compatible imported policy fields. Evaluate direct policy editing during I12 using real rule coverage. | Project owner and accounting implementer |
| Bridge and minimum Android level | Pilot in-process Python from Kotlin and provisionally support API 26 and higher. Decide after verified native packaging and parity. | Android implementer and project owner after I02 |
| Backup and OS testing | Keep canonical records private and use explicit share and restore. Verify Windows and Linux using actual GUI entry points. Identify the Windows test environment before release rehearsal. | Project owner and desktop test owner |
| Release identity and approval | Confirm the permanent app ID, account type, publisher identity, key custody, tester group and rollout. Recheck Play requirements before every upload. | Play account owner |

## Specification review checklist

- [x] The pinned reference identifies source and published desktop build. Every inventoried workflow has a disposition, a rule or source, and an acceptance case.
- [x] All in-scope parity rows link to editable-sourced annotated screen images. Report and maintenance flows cover shared states for empty, error, cancellation and recovery.
- [x] Kotlin and Compose UI, the CLI/library boundary, compatible private JSON, Share and restore are specified with verification gates.
- [x] Android Studio, virtual or physical phones, testing and Play account and release steps have beginner walkthroughs.
- [x] Implementation is divided into bounded, reviewable checkpoints with commits and passdowns.
- [ ] Complete the owner walkthrough of the menus, report routes, Settings and Help using the linked mockups and route table.
- [ ] The owner reviews draft choices and approves implementation.
- [ ] Run the bridge proof of concept, all Android acceptance cases, and the Linux and Windows GUI round trips on the real builds before release.
